# Examples

Small working examples, one per feature. CI builds each one and runs it headless with its
output checked exactly, so the code and calls here are known to work with this version of the
engine. Copy from them.

| Example | Shows |
| --- | --- |
| [components-and-systems](components-and-systems/) | A game's own component and a system that moves it, in C++ |
| [job-system](job-system/) | Threaded systems on the job system: systems whose reads and writes don't clash share a stage and run at once, one shares its work out with `parallel_for` and makes entities through `World::defer`, and the same ticks on no worker threads and on four give the same world |
| [gameplay-code](gameplay-code/) | A game's own C++ code in `src/`, built with `gameplay.build` and changed while the game runs: the world keeps its entities and fields, and compiler errors come back with file and line |
| [build-check](build-check/) | `build.check` compiling only the gameplay files that changed (and those including a changed header) with nothing linked, and returning errors and warnings as data with the compiler's fix, which the agent applies |
| [api-search](api-search/) | `api.search`: the C++ to call, found by name or by what it does, with its signature, doc, header and the lines of verified examples that use it; here in a game's own code, where a function declared in a header is defined in a source file and passed to `add_system` |
| [sdk-package](sdk-package/) | A closed vendor SDK in an `sdk.json` package: per-platform libraries, defines, Info.plist and Android manifest entries, an Android library folder, keys from the environment and glue code that adds an analytics backend in C++, Java and Objective-C; `sdk.check` lists its problems, `sdk.add` adds another, and exports build and link it |
| [ai-provider](ai-provider/) | A shopkeeper who talks through a language model behind `ai::Provider`: `providers.json` with a role, a streamed answer on a thread while the game ticks, an answer checked against a JSON Schema, an engine command run from the model's tool call, and the same answers again from the replay file with no model |
| [ai-dialogue](ai-dialogue/) | A baker who talks through a language model from gameplay code: `ai::ask` when a button is pressed, the reply as an `ai_reply` event shown in a label, the conversation kept in a component, `events.read` for agents, and the same conversation from the replay file in a session without the network capability |

## What an example holds

- `README.md`: what it shows and what to notice.
- `main.cpp`: a C++ program, built as `example-<folder>`. Its output is `expected.txt`.
- `calls.jsonl`: JSON-RPC requests for `slash-cli rpc --project .`, the same calls an agent makes
  as MCP tools (`entity.create` is the tool `entity_create`). `results.jsonl` holds the
  responses, line for line.
- `project.json`, scenes, prefabs and a storyboard when the example is a game project. It must
  pass `slash-cli project validate`.

## Running and adding examples

`ctest --preset dev -R example` runs every example in a copy of its folder under
`build/dev/examples/`, and fails if any output differs from what is checked in.

To add one, make a folder with a `README.md` and a `main.cpp` or `calls.jsonl`, link it in the
table above, then write its expected output and read it before committing:

```bash
cmake --preset dev && cmake --build --preset dev
SLASH_UPDATE_EXAMPLES=1 ctest --preset dev -R example_<folder>
```

Every new feature ships with an example here.
